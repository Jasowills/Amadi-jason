id: ADR-004
title: Kubernetes on AKS, because SSH and hope doesn't scale
summary: Git as the source of truth for every deploy.
date: 2025, Q1
---

I used to deploy with bash and prayer. Helm and ArgoCD made git the source of truth: every deploy a commit, every rollback a revert. The YAML tax is real, but so is sleeping through the night.

## Context

The platform now runs 10-plus services across development, staging, and production, each with different resource profiles, scaling requirements, and configuration needs. We needed a consistent orchestration layer for service discovery, load balancing, automatic restarts, rolling deployments, and horizontal scaling, without bespoke infrastructure scripts per environment. I have managed environments with custom scripts, and they do not scale past a handful of services before becoming a maintenance nightmare.

## Decision

Adopt Kubernetes on Azure (AKS) as the container orchestration platform. Package each service as a Helm chart with environment-specific value overrides, and use ArgoCD for GitOps-based continuous deployment. Namespace-level resource quotas and network policies enforce multi-tenant isolation within the cluster.

## Why

I used to deploy with SSH and hope; it breaks around service five. Kubernetes on AKS with Helm and ArgoCD made git the source of truth: every deploy a commit, every rollback a revert, every diff auditable. HPA handles spikes, self-heal handles the 3am crash. The YAML tax is real, but so is sleeping through the night, and the managed control plane buys a small team back hours.

## What it bought

- Declarative, GitOps-driven deployments keep environments consistent and leave a full audit trail of infrastructure changes in Git history, which I consider essential.
- Auto-scaling and self-healing reduce operational toil; the cluster responds to load and failures without manual intervention during off-hours.
- The tooling ecosystem (Helm, ArgoCD, Prometheus, Grafana) provides a mature operational stack out of the box.

## What it cost

- The learning curve is real; Kubernetes concepts (pods, services, ingress, CRDs) take ramp-up time and ongoing education that pulls engineers away from feature work.
- YAML-heavy Helm configuration gets difficult to maintain and debug as charts grow, and I have spent too many hours debugging template rendering issues.
- Operational overhead is disproportionate for a small team; cluster upgrades, node management, and network policies consume time that could go to product work.
