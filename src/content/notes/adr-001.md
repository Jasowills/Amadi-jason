id: ADR-001
title: Why Postgres, not Mongo, for the core
summary: Row-level security moves the bouncer into the database.
date: 2024, Q3
---

I got tired of chasing tenant leaks at 2am. Row-level security moves the bouncer from my app to the database, one place to get it right. ACID for billing, PostGIS so I can ask which vans are near Yaba without spinning up another service.

## Context

We needed a primary database for a multi-tenant platform with deeply nested relationships. Organizations contain projects, tasks, assigned users, and cascading permissions. Beyond that, we run reporting queries that aggregate data across tenants and join multiple entity types, and compliance demands strict isolation between tenants. I have seen document stores work well for simpler apps, but this domain is relationship-heavy and reporting-heavy, which changes the calculus.

## Decision

Use PostgreSQL as the sole database for core application data. Implement row-level security (RLS) policies at the database layer to enforce tenant isolation, and leverage PostGIS for the geospatial queries our field operations features need.

## Why

I picked Postgres because I was tired of getting paged for tenant leaks. RLS puts the bouncer in the database: one place to get isolation right, not a dozen app checks I can forget. ACID for billing is non-negotiable, and PostGIS lets me ask which vans are near Yaba without adding another service to babysit at 2am. I have used document stores where they fit; here the relationships and reports would have fought us the whole way.

## What it bought

- ACID transactions guarantee consistency across billing, audit logs, and entity state changes even under high concurrency, which is critical for a platform that moves money.
- Row-level security enforces tenant isolation at the database layer, shrinking the attack surface and removing reliance on application-level checks that are easy to get wrong.
- Joins, CTEs, window functions, and full-text search handle complex reporting without external indexing services.

## What it cost

- Schema migrations need careful planning and coordinated rollouts once the schema settles, and I have learned the hard way that rushed migrations cause outages.
- Vertical scaling has practical limits; read replicas and connection pooling add operational complexity as throughput grows.
- Rigid schema enforcement carries more risk on structural changes than a flexible document store, so we invested in solid migration tooling upfront.
